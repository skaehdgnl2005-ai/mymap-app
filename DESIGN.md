## Problem Statement

Korean Gen Z users (20s) screenshot cafe and restaurant recommendations from
Instagram, Threads, Naver blogs, and 캐치테이블, save them in their phone's
Notes app, then never visit because the cognitive cost of opening Naver Map
and searching one place at a time is too high. The discovery surface
(Instagram, Threads, 캐치테이블) is visually rich and curated; the navigation
surface (Naver Map, Kakao Map) is dense, info-heavy, and hostile to browsing.
There is a real friction gap between how Korean Gen Z discovers places and
how they navigate to them.

## Demand Evidence

- **Specific user (founder's friend):** 40+ saved places in phone Notes,
  returns to the same 3 cafes in 성수동 weekly because she can't decide among
  saved places. Her behavior demonstrates real demand for a low-friction
  discovery → visit flow, not just a storage container.
- **Toss precedent:** Toss proved Koreans will switch financial apps purely
  on UX in a deeply habituated category. Map apps in Korea have not visually
  evolved in a decade — same opportunity space.
- **Cultural shift:** Younger Korean users discover places via visual /
  curated content (Instagram, 오늘의집, 캐치테이블) but the "go there" step
  routes through dense, ugly maps. The bridge between discovery and
  navigation is missing.

## Status Quo

The current workflow Korean Gen Z users follow today:

1. See cafe on Instagram / Threads
2. Screenshot or save place name to Notes app
3. Later, when planning to go: open Notes app, find place name
4. Switch to Naver Map / Kakao Map
5. Type place name into search
6. Pick correct result from cluttered results list
7. Navigate

**Workaround cost:** ~6-7 steps with 2-3 app switches per place. Friction so
high that most saved places never get visited (founder's friend has 40+
saved, visits 3 weekly).

## Target User & Narrowest Wedge

**Target user:** Korean 20s, Seoul-centric, screenshots cafes from
Instagram, has dozens of saved places they never visit. Specific named
example: founder's friend with 40 places in Notes, three cafes in 성수동 on
rotation.

**Narrowest wedge:** A personal map where saving a place from Instagram is
1-3 taps and seeing all your saved places visually on a Toss-style minimal
map removes the "what was that cafe again?" friction entirely. NOT a search
engine. NOT an editorial guide. NOT social. Just: your places, on a beautiful
map, accessible faster than the current workflow.

## Constraints

- Must work reliably in South Korea (Google Maps data limitations make Google
  a non-option)
- Custom Toss-style visual rendering required (rules out closed map SDKs
  like Naver Maps / Kakao Maps which don't allow base-style customization)
- Cross-platform target: iOS, Android, web (web deferred to v1.5)
- React Native + Expo runtime
- Idea-stage budget — minimize commercial license dependencies in v1
- Single founder, no curation team

## Premises

**P1.** Defensible value is *workflow compression* (Instagram → at the door
in fewer steps), not visual polish. Polish is the marketing wrapper.

**P2'.** The moat is *user-data lock-in + workflow habit*, not editorial
curation. Every place a user saves makes the app harder to leave.
*(Revised from initial P2 in D3 — strictly stronger framing. Same model as
Notion vs Docs, Things vs Apple Reminders.)*

**P3.** Tile rendering and POI search will come from different sources. The
"custom map style" deliverable is one half of a two-system architecture; the
other half is a POI-search adapter (Kakao Local API).

## Approaches Considered

### D1 — Mode

**Decision:** Startup mode. User is building a real product, not a hackathon
demo. This routes to the YC forcing-question framework (compressed since
user already had specifics) and prioritizes pressure-testing demand over
generative riffing.

### D2 — Premise check

**Decision:** Locked P1, P2 (later revised to P2'), P3.

### D3 — Catalog scope

**Considered:** (A) Closed catalog only — editorial picks; (B) Open + curated
overlay — search any Korean POI with picks elevated; (C) Hybrid — closed home
+ search fallback; (D) Closed + user-added.

**Decision:** **Personal user-curated map** (user pushback created this
option). The user IS the curator of their own map. No editorial team needed.
Each user's saved places become their personal map. Reframes P2 from
"editorial curation as moat" to P2' "user-data lock-in as moat."

### D4 — Rendering stack

**Considered:** (A) Mapbox full stack; (B) MapLibre + MapTiler; (C) MapLibre
+ self-hosted OpenMapTiles.

**Decision:** **MapLibre-compatible Mapbox Style Spec v8 written for Mapbox
runtime in v1, with planned migration to MapLibre + MapTiler post-PMF.** User
revised the recommendation to keep Mapbox runtime in v1 (free up to 50k MAU,
@rnmapbox/maps maturity) while keeping the Style JSON portable for migration.
Style Spec v8 is identical syntax across both runtimes.

### D5 — POI provider

**Considered:** Kakao Local API vs Naver Cloud Platform Maps.

**Decision:** **Kakao Local API.** Primarily for licensing — Kakao's
developer terms explicitly permit using their POI data with custom map
rendering (with attribution); Naver's TOS restricts overlay on non-Naver
renderers and requires commercial license negotiation. Secondarily for
quota: 100k req/day pooled vs Naver's 25k/25k/25k split. Escape hatch:
Naver upgrade via NCP commercial license at v2 if POI freshness gap
materializes.

### D5b — POI provider re-resolution (v1 access constraint)

**Status:** ADDITIVE to D5 (D5 본문 unchanged). D5 stays correct as
the intended production target; D5b is the v1 transitional fallback
forced by an access constraint discovered during Phase 5.

**Decision:** v1 development + friend-demo + initial cohort runs on
**Naver Open API Local Search** (`developers.naver.com`,
`/v1/search/local.json`), NOT Kakao Local API.

**Trigger:** Kakao Developer Console requires 사업자 등록
(business registration) to activate the 카카오맵 product on a
developer app. The founder is not in a position to register a
business at v1. This is a hard access constraint, not a technical
preference. Discovered 2026-05-07 during Phase 5 Track A emulator
verification (HTTP 403 `App(map) disabled OPEN_MAP_AND_LOCAL
service`).

**What changed (vs D5):**

- POI provider for keyword search + place resolution: Kakao → Naver
- Authentication: `Authorization: KakaoAK <key>` → `X-Naver-Client-Id`
  + `X-Naver-Client-Secret` headers
- Daily quota: 100k Kakao → 25k Naver (still well within v1 cohort
  per success criteria target of 30 users by week 4)
- Result coordinates: Kakao decimal-string WGS84 → Naver integer
  WGS84 × 10⁷ (one-line conversion `parseInt(x)/1e7`, no proj4
  dependency). Empirically verified 2026-05-07 against real query
  "어니언 성수" → `mapx=1270581051` → `127.0581051` (성수동 정확
  매칭). The official Naver doc has an inconsistency — text says
  "WGS84 좌표계 기준", sample shows 2016-era KATECH values —
  resolved in favor of doc text + empirical confirmation; see
  Verification Principles Case #4 for the general lesson.
- Result max per query: 15 (Kakao) → 5 (Naver). Manual search UX
  slightly worse for ambiguous queries; friend-demo on 성수 cafes
  has been verified to return adequate matches with 5.
- Provider place_id: Kakao stable id → Naver none. Affects dedup
  if we ever want "external_place_id" lookup. v1 code doesn't use
  external place_id (SavedPlace.id = Supabase uuid). Future
  mitigation if needed: synthesize stable hash from
  `(name + jibun_address)`.
- HTML `<b>` tags wrap matched substring in Naver `title` — client
  strips with one regex.

**What stays from D5:**

- POI rendering on Mapbox (custom) tiles. Naver Open API TOS allows
  search-result display in 3rd-party apps; D5's "Naver TOS restricts
  overlay on non-Naver renderers" concern was about NCP Maps SDK
  (the rendering SDK product), not the Open API Search product —
  separate TOS, separate license.
- Korean POI coverage requirement.
- Attribution requirement: "Powered by Kakao" → "Powered by Naver"
  (TOS-required for Naver Open API).
- `spec/data-shapes.ts` `KakaoPlaceResult` interface stays
  (renamed conceptually as the common provider-narrowed shape;
  both providers map cleanly into it).

**Migration path back to D5 (Kakao Local API):**

1. Founder obtains 사업자 등록증 (or a co-founder/family member
   with one onboards as the Kakao app admin).
2. Activate 카카오맵 product in Kakao Developer Console.
3. Restore `src/kakao/client.ts` from archived state (preserved
   in repo with archive header comment, never deleted, per D5b
   implementation policy).
4. Swap `src/save-flow/SaveModal.tsx` import: `naver/client` →
   `kakao/client`.
5. Swap `.env`: `EXPO_PUBLIC_NAVER_CLIENT_ID/_SECRET` →
   `EXPO_PUBLIC_KAKAO_REST_API_KEY`.
6. Update attribution back to "Powered by Kakao".
7. Smoke-test 5 save paths.

**Phase 10 evaluation gate (before App Store / Play Store launch):**

Re-evaluate POI provider:

- (a) Kakao biz reg viable by then → migrate per above. Preferred
  long-term: better quota, stable place_id, distance field, larger
  per-query result set.
- (b) Naver Open API still meets demand (quota + freshness + TOS
  compliance) → continue, add the "Powered by Naver" attribution
  to App Store screenshots + Phase 10 ToS doc.
- (c) Neither (e.g. both API surfaces tightened, founder still no
  biz reg) → architectural pivot to one of: OSM Nominatim
  hybrid for Korean POIs / Mapbox Search Box (commercial license
  via Mapbox account) / "drop pin on map, no provider search"
  flow (significant wedge re-think).

**Implementation files affected:**

- NEW: `src/naver/client.ts` — mirrors `src/kakao/client.ts`
  shape, Result<T> tagged union preserved, mapx/mapy ÷ 1e7
  conversion, Korea-bbox sanity assert as fail-fast guard against
  format changes, `<b>` tag strip in title.
- ARCHIVED: `src/kakao/client.ts` — kept in repo with archive
  header comment, code unchanged. Migration target per D5b
  reverse path.
- MODIFIED: `src/save-flow/SaveModal.tsx` — single-line import
  swap + attribution string change.
- UNCHANGED: `app.config.ts` — credentials are in `.env`, not
  Expo plugin config.
- MODIFIED: `.env.example` — adds `EXPO_PUBLIC_NAVER_CLIENT_ID`
  + `EXPO_PUBLIC_NAVER_CLIENT_SECRET`.
- MODIFIED: `App.tsx` — boot-log assertion extended to include
  naver presence flag.

**Sanity-check evidence in support of D5b** (verified 2026-05-07):

1. Schema verified verbatim from `naver/naver-openapi-guide` GitHub
   repo: `ko/service-apis/search/local/local.md`.
2. Field-by-field comparison with Kakao Local: 0 critical losses
   for v1 use case; minor losses (`category_group_code`, `phone`,

3. Coordinate format: WGS84 × 10⁷ integer (NOT KATECH despite one

### D6 — Data model

**Considered:** (A) Bare minimum; (B) Pragmatic v1 with OG cache; (C) Rich
v1 with photos.

**Decision:** **Pragmatic v1, 15-field schema** including the load-bearing
`source_url` field plus 5 OG metadata cache fields, anchor categories
(HOME/SCHOOL/WORK), color tags, visited boolean. See `spec/data-shapes.ts`
for the full type. Photos deferred to v2 (adds 6-8 weeks for photo upload UX
+ CDN + offline cache).

### D7 — Save flow

**Considered:** (A) Share-sheet only; (B) Share-sheet + clipboard + smart
resolve; (C) + OCR; (D) Manual paste only.

**Decision:** **B with per-platform routing primacy.** Share-sheet primary
for Naver/Kakao Place URLs and blog posts; clipboard primary for
Instagram/Threads (Instagram's share-sheet UX deprioritizes external apps,
making "Copy link → switch to MyMap → +" the actual primary path). Smart
resolve: Naver/Kakao URLs auto-resolve to 1-tap save; Instagram/blog URLs
route through Kakao keyword-search modal where user picks the matching place.
Clipboard auto-detect fires on `+` button tap (user-initiated), NEVER on app
foreground (Toss principle: peek clipboard at the moment user would want
help, not on session start).

### D8 — Cold-start onboarding

**Considered:** (A) Anchor-only seed; (B) Anchor + 3 favorite places;
(C) Location-history; (D) Notes paste with NLP.

**Decision:** **Stripped-down B — anchor-only 2-step.** Set HOME, then
SCHOOL/WORK toggle. No favorite-pin seeding. The "set 3 favorite places"
step from initial recommendation B was cut because it conflicts with the
"evolving canvas" identity (asks user to do the exact cognitive work they
came to escape). Empty map = intentional product statement. Persistent hint
card "+ 인스타에서 본 카페를 저장해보세요" carries comprehension. ~30 seconds
total onboarding. No NLP, no permissions during onboarding.

**Implication:** D8 (visual system) carries comprehension work that the cut
3 pins would have done. Visual quality is not optional — it is load-bearing.

### D9 — Visual foundation

**Considered:** (A) Warm cream + coral; (B) Cool off-white + deep indigo;
(C) Warm gray + electric blue.

**Decision:** **B — cool off-white base + deep indigo brand**, with the base
warm-shifted to `#F5F4F0` (eliminates clinical feel without losing editorial
register). Brand color `#2D2A6B` claims unoccupied territory in Korean app
landscape (none of 당근/토스/네이버/카카오/무신사/오늘의집 sit there). The
risk taxonomy was the deciding frame: "tunable risks (palette feel) are
cheap; category-perception risks (looks like 당근, looks like Toss) are
existential." Subway lines preserved at canonical hue but desaturated to
~40% to not fight brand. Bus lines deferred to v1.5. Full 13-color light +
13-color dark palette with token-pair pattern (see `spec/tokens.json`).
Typography: Pretendard, weights 400/500/700 for UI, 400/500 for map labels.

### D10 — Marker shapes

**Considered:** (A) Teardrop + rounded square; (B) Circle (expands to
teardrop on tap) + rounded square; (C) Pill with inline name + rounded
square.

**Decision:** **B — circle saved-pin (expands to teardrop on tap) +
rounded square anchor pin.** Toss-minimal default state, reveals lat/lng
pointer when precision matters (selected). Round vs square pairing maps
cleanly onto "anchors = infrastructure, saved places = content"
distinction. Visited state = outlined indigo (filled = to-go,
outlined = visited; no opacity tricks, no badges). Color tag = filter only
(activates fill when user enables filter; default view all-indigo;
indicator appears in popover, NOT on map pin). Cluster spec: 24px uniform
bubble (count is the variable, bubble is constant), saved pins only,
anchors don't cluster.

### D11 — Icon set + visual polish

**Decision:** 9 single-outline geometric glyphs designed for 10-12px
legibility:

| Category | Glyph |
|---|---|
| CAFE | Coffee cup silhouette (no saucer, no handle) |
| RESTAURANT | Rice bowl semicircle |
| BAR | Wine glass triangle on stem |
| SHOP | Bag with handle-cutout (single continuous outline) |
| LANDMARK | 5-point star |
| OTHER | Diamond (rotated square — avoids the "kebab menu" pattern-match of three dots) |
| HOME | Pentagon house |
| WORK | Briefcase with handle-cutout (single continuous outline) |
| SCHOOL | Open book V-shape |

**Halo:** 1.5px stroke at `#1A1850` (light mode — die-cut effect, uniformly
visible across all base surfaces) / `#1B1A18` (dark mode — surface-matched).
Selected state: stroke widens to 2.0px.

**Shadow:** NONE (Toss-flat aesthetic, dark-mode consistent, cheaper render).

**Sprite pipeline:** 9 SVG canonical sources in git → `spreet` CLI →
sprite.png + sprite.json → self-host on R2/Supabase Storage (NOT
Mapbox-hosted). Style JSON references local URL.

### D12 — Zoom-level visibility rules

Anchors visible at zoom ≥ 12. Saved pins individual at zoom ≥ 14
(clusters render at zoom 12-13 at 18px @ 80% opacity; full 24px at zoom
14+). Subway hub lines (1, 2, 3, 4, 9) at zoom 13. All subway lines +
station dots at zoom 14, with **transfer stations distinguished** (larger
dot + outline, name appears one zoom earlier than regular stations — Korean
users navigate by 환승역 as spatial anchors). Brand color **never** on
labels — subway identity carried by line colors; labels use text_primary /
text_secondary. Italic = natural features only (parks, water).

Building labels deferred to v1.5 (curation rabbit hole; Korean addresses
carry wayfinding load anyway).

Mobile-first interactions: tap-only (no hover); long-press = quick-action
menu; two-finger rotate disabled in v1.

## Recommended Approach

Build the personal-map app with the locked architecture above. Phase
sequence:

**Phase 1 (v1):** Ship the Style Spec + sprite + glyphs + RN integration to
render the base map with anchor + saved pins. Implement save flow
(share-sheet + clipboard) with smart resolve. Implement 2-step onboarding.
Implement Kakao keyword search + auto-resolve for Naver/Kakao URLs. Sync to
chosen backend (Supabase or Firestore).

**Phase 2 (v1.5):** Refine OG fetch reliability for Instagram (best-effort
+ graceful degrade), add data export (CSV/GeoJSON), add "search nearby"
edge case, optionally add bus lines if usage data shows demand, optionally
add building labels for landmarks if usage data shows search-by-building.

**Phase 3 (post-PMF):** Migrate runtime from Mapbox to MapLibre + MapTiler
per the migration checklist in `README.md`.

## Success Criteria

v1 is successful if:

- Founder's friend (specific named user) saves 5+ places from Instagram in
  week 1 of beta
- Average save-flow time (Instagram → on map) is under 15 seconds for
  Naver/Kakao URLs, under 30 seconds for Instagram URLs
- 30+ users in week 4 each have ≥10 saved places (lock-in evidence per P2')
- Cluster behavior holds at 50+ saved places without performance degradation
- Visual identity is consistent enough that a screenshot is recognizable as
  "MyMap" without branding text (per the "considered marks against quiet
  base" thesis from D9)

## The Assignment

**Build a working save-flow prototype this week.** Specifically:

1. Pick a Naver Place URL (e.g., a 성수동 cafe).
2. Build a 30-line React Native app that:
   - Opens with the share-sheet receiving the URL
   - Calls Kakao Local API to resolve the place
   - Displays the place name + a map preview
3. Test it with your friend (the named user) — does she save 3 places to it
   within 10 minutes of using it?

This is the smallest possible end-to-end test of the wedge thesis. It does
NOT need: design polish, the Toss-style base map, anchor pins, OG cache, or
any other piece of the locked spec. Those come after the core flow is
validated as feeling fast.

The reason: every spec decision in this doc assumes the save flow IS the
product. If she saves 3 places in 10 minutes, you're building a real product.
If she gets stuck or the flow feels clunky in real use, you've discovered
the real bottleneck before investing in the visual system.

**Time-box: 2 days max.** Use any UI library (NativeBase, Tamagui, plain
RN). Don't sweat the visuals — that's what the locked spec is for, later.
